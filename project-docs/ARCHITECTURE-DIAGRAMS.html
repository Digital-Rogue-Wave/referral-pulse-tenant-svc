Claude Code Configuration

Architecture diagrams for the ReferralAI NestJS microservices platform — 9 services, 6 agents, 3 tiers of context loading

1Three-Tier Context Loading

How Claude Code assembles its context window at startup. Only 548 lines are always loaded. 4,672 more are available on demand — loaded one file at a time when an agent needs a specific pattern.

Why this matters: Only ~548 lines are always loaded (~2,200 tokens). The other 4,672 lines are available but never enter context unless an agent specifically needs one file. This keeps the context window clean for your actual code work — you get ~3 hours of productive session instead of 30 minutes.

2Runtime Prompt Flow

What happens from the moment you type a prompt to the final code output. Shows how hooks, rules, agents, and MCP servers interact at each step.

Key insight: Hooks are deterministic (Node.js scripts, not AI). Rules are probabilistic (instructions that shape behavior). Both work together — hooks enforce hard limits (100-line files, no uuid(), no rm -rf). Rules enforce soft guidelines (SOLID, naming). If Claude's rules drift over a long conversation, hooks still catch violations.

3Agent Delegation Map

Six specialized agents, each with a specific model, trigger condition, and capability. Sub-agents run in their own context — verbose output stays isolated from your main conversation.

Sub-agents protect the main context. When @debugger greps 50 files or @code-reviewer reads the full git diff, that output stays in the agent's context window. Your main conversation only sees the summary. This is why long sessions stay productive.

4Hook Enforcement Pipeline

The deterministic safety net. These are Node.js scripts — not AI. They can't be persuaded, hallucinated, or prompt-injected. They run before and after every tool call.

Why hooks matter: Even if Claude's rules drift after 50 messages, even if it "forgets" that files should be < 100 lines, the hook will still block the write. Hooks are the hard floor that never moves. They're your insurance policy against long-session drift.

5Self-Improvement Loop

How tasks/lessons.md compounds over time. Most configs are static — same quality on day 1 and day 100. This one gets smarter every day because every correction becomes a permanent rule.

The compound effect: Memory Keeper adds another layer — architectural decisions persist across sessions without cluttering lessons.md. Together, lessons.md (corrections) + Memory Keeper (decisions) mean every session starts smarter than the last.

6Multi-Microservice Architecture

How the config works across all 9 services. Same config everywhere — only CLAUDE.md has a per-service section. The infrastructure repo runs all dependencies via Docker Compose.

Why identical configs work: Every service follows the same coding standards, the same patterns, the same testing rules. When a developer switches from reward-service to campaign-service, Claude Code behaves identically. The only difference is the "This Service:" section that tells Claude what this specific service owns, publishes, and consumes.

7Supervised Workflow (Phase Gates)

The full feature development flow from user story to commit. Each phase is a gate — Claude stops and waits for your explicit approval before continuing.

Supervised vs Autonomous: Start every session with "Work in SUPERVISED mode." As you build trust with the config over days/weeks, relax specific gates. Eventually, for well-defined tasks, use "Work in AUTONOMOUS mode" — Claude runs all phases and presents the final diff. Hooks still enforce all rules regardless of mode.

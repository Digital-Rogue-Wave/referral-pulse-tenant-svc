# 2. Core Concepts & Glossary

## Primary Entities

| Entity | Definition |
| --- | --- |
| **Program** | Top-level container representing a client's entire referral operation. One program per client. |
| **Campaign** | A discrete referral initiative with specific goals, schedule, pulse type, and budget. Contains variants. |
| **Variant** | A complete configuration bundle within a campaign. Bundles: a segment reference (WHO gets this) + reward config (WHAT incentive) + messaging (WHAT copy) + allocation weight (HOW MUCH traffic). A variant is NOT a segment — it references a segment. |
| **Pulse** | A workflow template that defines trigger logic (e.g., Signup Pulse triggers on account creation, Conversion Pulse triggers on payment). |
| **Playbook** | A vertical-specific configuration bundle combining recommended Pulses, rewards, and settings. Playbooks are curated by our team, not generated by AI. The AI can recommend which playbook fits a client's situation. |
| **Participant** | An external actor who refers others. NO platform access — interacts only via links, widgets, emails. |
| **Referee** | A person who is referred by a participant and becomes a customer. |
| **Referral** | The tracked relationship between a participant (referrer) and referee (referred). |
| **Segment** | A reusable audience definition — a set of rules that answers "does this person belong to this group?" Segments exist independently of campaigns and can be shared across multiple variants. A segment is the filter; the variant is the package delivered to people who pass the filter. |
| **Reward** | The incentive granted to participants (and optionally referees) for successful referrals. |
| **Touch** | A recorded interaction in the referral journey (click, share, visit, email open). |
| **Attribution** | The process of assigning credit for a conversion to the correct participant(s). |
| **Enrollment Model** | All campaigns use selective enrollment: only pre-enrolled participants see the widget. Non-enrolled users see nothing. Participants must be registered in our platform via API, CSV import, or CRM sync before they can share referral links. |
| **Default Variant** | Auto-created variant that every campaign has. If client defines no variants, the default variant holds the campaign's reward/messaging config. Acts as catch-all fallback in multi-variant campaigns. |

## Entity Hierarchy

**Entity Hierarchy**

- Program
- 1 per client

- Campaign

- pulse_type · schedule · budget

- **Variant A** segment · reward_config messaging · eligibility
- **Variant B** segment · reward_config messaging

**Key Design Decisions:**

1. Reward configuration is at the **Variant** level, not Campaign level. This enables segment-specific incentives within a single campaign.
2. Every campaign always has at least one variant — the **Default Variant**. If the client creates a simple campaign without defining variants, the system auto-creates a default variant holding the campaign's reward and messaging config. In multi-variant campaigns, one variant can be marked as default to serve as a catch-all for participants who don't match any segment.
3. **Selective enrollment only.** Only pre-enrolled participants see the widget. Non-enrolled users see nothing — they don't know the referral program exists. The client controls exactly who can refer by registering users via API, CSV import, or CRM sync. There is no self-enrollment via widget.
4. **Variant ≠ Segment.** A Segment is a reusable audience filter ("who"). A Variant references a Segment and adds reward config, messaging, and allocation weight ("what they get"). Multiple variants can reference the same segment. A variant always has exactly one segment reference.

## What Lives Where

| Config | Level | Rationale |
| --- | --- | --- |
| Pulse type | Campaign | Same trigger logic for all variants |
| Schedule | Campaign | Unified start/end |
| Budget | Campaign | Shared budget pool |
| Segment target | Variant | Different audiences |
| Reward config | Variant | Different incentives per segment |
| Messaging | Variant | Personalized copy |
| Eligibility rules | Variant | Segment-specific requirements |

### Campaign States

`Draft` → `Scheduled` → `Active` → `Paused` → `Ended` → `Archived`

### Participant States

## Extended Concept Model

The glossary above defines the primary entities. This part of the section (a) adds the concepts the domain needs but the glossary left undefined — **Event, Conversion, Eligibility, AI Recommendation, AI Decision, Human Override, Fraud Signal, Program Health Score** — and (b) makes the relationships between *all* concepts explicit, so the rest of the document can reference them precisely.

### Concept Additions (Glossary Δ)

| Concept | Precise Definition | Why It Exists |
| --- | --- | --- |
| **Event** | An immutable, timestamped, append-only fact that something happened (`referral.clicked`, `conversion.recorded`, `reward.approved`). Events are the system's source of truth; every projection, attribution result, reward, and analytic is derived from the event log. | The platform is event-first (immutable design constraint). Events decouple domains: a producer emits a fact and never knows who consumes it. |
| **Touch** *(refined)* | A specific *sub-class* of Event that belongs to the referee-side journey and carries attribution context (click, share, view, email-open, email-click). Every Touch is an Event; not every Event is a Touch (e.g. `reward.approved` is an Event, not a Touch). | Separating Touches from Events lets Attribution operate on a small, well-typed slice of the log without scanning every fact. |
| **Conversion** | The Event in which a Referee completes the campaign's qualifying action (defined by the Pulse: signup, first payment, renewal…). A Conversion references the Referral it satisfies and the monetary value (if any) for revenue attribution. | The Conversion is the hinge between tracking and money: it closes a Referral and triggers Reward calculation. Revenue-first analytics require the Conversion to carry MRR/ARR, not just a boolean. |
| **Eligibility** | A *decision function* evaluated at a checkpoint (entry, referral, conversion, reward, payout) that returns allow/block + reason. Eligibility is stateless w.r.t. its inputs (Participant attributes, campaign state, caps, fraud score) — it reads, it does not mutate. | Centralizing allow/block logic into named checkpoints (already in §5) makes the rules auditable and lets Compliance and Fraud hook the same gates. |
| **Fraud Signal** | A single observation that raises or lowers risk for an Event or Participant (self-referral match, velocity spike, disposable email, device-fingerprint collision). Signals are inputs; they are not decisions. | Modeling signals as first-class lets the Fraud service explain a score ("blocked because: device match + velocity") — required by the Explainable AI principle and by GDPR auditability. |
| **AI Recommendation** | A proposed change or insight emitted by an AI capability, always with (i) a rationale, (ii) the data window it used, and (iii) a confidence. A Recommendation *never* mutates state on its own. | Makes "AI-embedded, human-in-the-loop" concrete: the default AI output is advisory and overridable. |
| **AI Decision** | An AI output that *does* mutate state, permitted only inside pre-declared bounds (e.g. incentive change ≤ `auto_approve_below`, fraud auto-block at score > 0.8). Every Decision is reversible and audit-logged with its triggering Recommendation. | A narrow, bounded escape hatch from "advisory only" for cases where waiting for a human is worse (live fraud) or trivially safe (sub-threshold reward tweak). |
| **Human Override** | An operator action that accepts, edits, rejects, or reverts an AI Recommendation or AI Decision. The Override is itself an Event and is the authoritative record for accountability. | Guarantees the "Overridable" principle is enforced structurally, not just by UI convention. |
| **Program Health Score** | A 0–100 composite, computed per Program, summarizing funnel performance, revenue impact, fraud pressure, and audience saturation into one tracked number with sub-scores. See §11. | Gives clients and the AI Insights Panel a single proactive signal ("your program is degrading") instead of forcing them to read ten dashboards. |

> **Revised Definition (Touch).** §2/§10 treat Touch and Event loosely as synonyms. This specification makes Touch a strict subtype of Event (referee-journey, attribution-bearing). This is additive: no existing Touch type changes.

#### Revised Definition: Three Orthogonal Participant Axes

§2, §7, and the task brief use "Advocate", "Active", "Dormant", "High-Trust" in ways that overlap. They are **three independent axes** and must not be collapsed:

| Axis | Values | Owned by | Answers |
| --- | --- | --- | --- |
| **Operational state** | Active · Dormant · Flagged · Suspended · Banned | Participant domain | "Can they act right now?" |
| **Trust level** | New · Established · Trusted · Advocate | Trust model (Lot 1) | "How much financial exposure do we allow?" |
| **Journey stage** | Anonymous → Candidate → Enrolled → Active Referrer → Earner → Advocate | Analytics projection | "How far along the relationship are they?" |

"**Advocate**" appears on two axes deliberately: it is the top *trust level* (score 76–100) and the final *journey stage*. A participant is a journey-stage Advocate when they are operationally `Active` and at trust level `Trusted` or `Advocate` with sustained earnings. They are distinct facts; §7 keeps them separate.

## Referral Tracking: Touch Capture Explained

**Touch** = Any tracked interaction between referral link click and conversion.

**Touch Capture** = The process of recording these interactions with full context.

| Touch Type | How Captured | Data Recorded |
| --- | --- | --- |
| **Click** | SDK detects `?ref=` parameter | ref_code, timestamp, referrer URL, UTMs, device, IP hash |
| **Share** | SDK tracks share button clicks | channel (LinkedIn, email, copy), timestamp, link variant |
| **Widget View** | SDK tracks widget render | page URL, duration, variant shown |
| **Page Visit** | SDK pageview tracking | URL path, referrer, session_id, time on page |
| **Email Open** | Tracking pixel in platform-sent email | invitation_id, timestamp, email client |
| **Email Click** | Redirect through tracking URL | link_id, timestamp, destination |

**Why Touch Capture Matters:**

1. **Attribution chain** — Determines which participant gets credit
2. **Multi-touch attribution** — Enables credit splitting (V2)
3. **Channel analytics** — Which channels convert best
4. **Fraud detection** — Suspicious timing/pattern detection
5. **Funnel analysis** — Where referrals drop off

## Bounded Contexts & Event Contracts

The domain table above lists nine domains and their responsibilities. This part gives each a **bounded context** (what it owns and what it must never own), its **entities/value objects**, its **inputs and outputs**, and a concise **event contract** (produced / consumed). Naming convention for events: `<aggregate>.<past-tense-verb>`, e.g. `referral.qualified`.

### Ownership Boundaries (anti-overlap)

**Who Owns the Truth**

```
Identity&Access  │ owns: User, Role, ApiKey, Tenant, JWT verification
Program&Campaign │ owns: Program, Campaign, Variant, Playbook, Schedule, Budget
Segmentation     │ owns: Segment, SegmentMembership, RandomAssignment
Referral Tracking│ owns: Link, Touch, Referral(open), Click/Share/View events
Rewards&Payouts  │ owns: Reward, RewardLedger, Payout, PayoutMethodRef, Hold
Analytics&Attr.  │ owns: Touch projections, AttributionResult, MRR/ARR rollups, Health
AI&Optimization  │ owns: Recommendation, Decision, ModelVersion, FeatureStore (derived)
Compliance       │ owns: Consent, DSR, RetentionPolicy, AuditLog, LawfulBasisTag
Integrations&API │ owns: Webhook subscription, Connector config, OutboundDelivery
                  ↑ each box writes ONLY its own RDS; everyone else reads via events/API
```

**Hard rule:** the *open* Referral lifecycle (Pending→Qualified→Converted) is owned by Referral Tracking; the moment a Conversion is priced, Rewards takes over the *monetary* lifecycle (Pending→…→Paid). Analytics owns no lifecycle — it only projects. This prevents the classic referral-platform bug where reward state and referral state drift apart in two services.

### Per-Domain Event Contracts

| Domain | Key Inputs (commands/API) | Produces (events/webhooks) | Consumes |
| --- | --- | --- | --- |
| **Identity & Access** | `POST /v1/api-keys`, JWT verify, role grants | `user.invited`, `apikey.created`, `apikey.revoked` | — |
| **Program & Campaign** | `POST /v1/campaigns`, publish, pause, set budget | `campaign.activated`, `campaign.paused`, `campaign.budget_threshold`, `variant.created` | `reward.approved` (budget burn), `recommendation.created` |
| **Segmentation** | `POST /v1/segments`, enroll, evaluate | `segment.membership_changed`, `variant.resolved`, `random.assigned` | `participant.enrolled`, `participant.attributes_updated`, propensity scores |
| **Referral Tracking** | SDK events, `POST /v1/events`, payment webhooks | `referral.created`, `referral.clicked`, `link.shared`, `referral.qualified`, `conversion.recorded` | `variant.resolved`, `fraud.scored` |
| **Rewards & Payouts** | conversion event, approve/reject, payout request | `reward.calculated`, `reward.held`, `reward.approved`, `reward.reversed`, `payout.sent` | `conversion.recorded`, `fraud.scored`, `participant.trust_changed` |
| **Analytics & Attribution** | (read-only) replay event log | `attribution.resolved`, `mrr.attributed`, `health.recomputed` | all Touch + Conversion + Reward events |
| **AI & Optimization** | training jobs, scoring requests, accept/override | `recommendation.created`, `decision.executed`, `propensity.scored`, `fraud.scored`, `participant.trust_changed` | analytics rollups, event log (feature store) |
| **Compliance & Privacy** | consent set, DSR submitted, retention tick | `consent.recorded`, `dsr.requested`, `erasure.completed`, `audit.logged` | everything (audit sink); `dsr.requested` fan-out |
| **Integrations & APIs** | webhook subscribe, connector sync | `webhook.delivered`, `webhook.failed`, `connector.synced` | every domain's public events (fan-out to client endpoints) |

### Cross-Domain Event Flow — Click to Payout

The canonical happy path, showing which domain acts at each step and the event that carries the baton. This is the backbone the Temporal pulse workflows (§6) orchestrate.

**End-to-End Event Flow**

```
 Referee clicks link
   │  Referral Tracking: referral.created ──────────────▶ Fraud: fraud.scored
   ▼                                                          │ (creation gate)
 [Eligibility: referral checkpoint] ◀───────────────────────┘
   │ allow
   ▼
 Referee signs up / pays
   │  Referral Tracking: conversion.recorded (value=€X MRR) ─▶ Analytics: attribution.resolved
   ▼                                                          └▶ Analytics: mrr.attributed
 Rewards: reward.calculated
   │  ├─ participant.trust_changed? ── reads Trust
   │  └─ fraud.scored (reward gate)
   ▼
 [decision] ── score<0.3 & trust auto-OK ─▶ reward.approved
   │           score 0.3–0.7 ────────────▶ reward.held ─▶ (human Override) ─▶ approved|rejected
   │           score>0.7 ─────────────────▶ reward.reversed/blocked + fraud alert
   ▼
 Program&Campaign: budget burn (campaign.budget_threshold at 80/100%)
   ▼
 Rewards: payout.sent ──▶ Integrations: webhook.delivered(reward.paid) ──▶ client endpoint
   ▼
 Compliance: audit.logged at every state change; Analytics: health.recomputed (nightly)
```

**Idempotency & ordering.** Every inbound command carries an `event_id` (already specified for `/v1/events`); consumers dedupe on it. Cross-domain consumers must tolerate at-least-once delivery and out-of-order arrival — e.g. a late `conversion.recorded` after `campaign.paused` is still processed (pipeline referrals honored, per §6 budget-exhaustion rule).

## External Actors (No Platform Access)

### Participant (Referrer)

**Critical Constraint:** Participants have NO platform login and there is no platform portal. All interactions via: - Referral links (unique per participant) - Embedded widgets (in client's app) - Email notifications (rewards, conversions, "ready to claim") - QR codes (for offline/events)

Payout method is collected in the widget or on the payout **partner's** hosted page (linked from email) — never on a RefRev-hosted page.

**Participant Capabilities:** - View their referral link and stats (via widget or email) - Share via social/email/copy - See pending and earned rewards - Set up payout method (via widget or partner-hosted page) - View referral history (widget/email)

### Referee (Referred Person)

**Definition:** Person who clicks a referral link and potentially converts.

**Lifecycle:** 1. Anonymous visitor (clicked link, has cookie) 2. Lead (provided email or signed up) 3. Customer (completed qualifying action — payment, subscription)

**Referee Capabilities:** - Click referral links - Receive referee rewards (if two-sided rewards configured) - No direct platform interaction

### Partner — Detail

A Partner is any external *system* the platform delegates a function to (≠ a high-trust Participant, which the brief's "User → Ambassador → Partner" path also calls "partner" — see lifecycle note below). Partners never receive more personal data than their function requires (data minimization, §12):

| Partner class | Receives | Returns | Residency constraint |
| --- | --- | --- | --- |
| Payout (PayPal, Wise, Tremendous) | Payout amount, currency, provider reference, PayPal email | `payout.sent` confirmation, failures | Prefer EU processing entity; never store raw bank data (§8) |
| Payment provider (Stripe, Paddle, Chargebee) | —(reads their webhooks) | Conversion + MRR via metadata | EU data region where offered |
| CRM (HubSpot, Salesforce) | Enrollment list selection | Contacts → Participants | Consent/lawful basis must precede enrollment email |
| Email/CMP (OneTrust, Cookiebot, Osano) | Consent state | Consent change callbacks | n/a (client-side) |

### Actor Lifecycles & Cross-Role Evolution

Two evolution paths the brief calls out, reconciled with §7's "no Candidate platform state" (Revised Definition in Appendix A).

#### Referee → Advocate (the flywheel)

**Referee becomes a Referrer**

```
 Referee (clicks link, anonymous)
   │ signs up
   ▼
 Activated User (in CLIENT system — not a platform participant yet)
   │ first payment / qualifying action
   ▼
 Paying Customer ── client enrolls them via API/CSV/CRM (§7) ─┐
                                                         ▼
                                          Enrolled Participant (Active, trust=New)
                                                         │ shares + drives conversions
                                                         ▼
                                          Earner (has approved rewards)
                                                         │ sustained quality, trust↑
                                                         ▼
                                          Advocate (trust Trusted/Advocate, journey-final)
```

> *The referee of one campaign becomes the referrer of the next — this is the growth loop the platform exists to close.*

#### User → Ambassador → Partner

**Revised Definition.** "Ambassador" and "Partner" here are *not* new platform entities — they are *configurations of a Participant* at high trust, typically served by an Agency Partner playbook:

| Label | What it actually is | Reward pattern |
| --- | --- | --- |
| **User** | Participant, trust New/Established, one-sided fixed reward | Fixed per conversion |
| **Ambassador** | Participant, trust Trusted, milestone + tiered rewards, email + widget stats | Tiered + milestone bonus |
| **Partner** | Participant, trust Advocate, recurring commission, instant payout, often agency segment | Recurring % for N months |

This keeps a single `Participant` aggregate (no schema fork) while letting messaging, rewards, and trust privileges escalate — supporting the **Agency Partner** and creator playbooks without new bounded contexts.

# 5. Segmentation & Eligibility

## Segment Types

| Type | Description | Example | Update Frequency |
| --- | --- | --- | --- |
| **Static** | Manually curated list | "Beta testers", "VIPs" | Manual |
| **Rule-Based** | Attribute filters | plan = "enterprise" AND mrr > 500 | Real-time |
| **AI-Generated** | ML clustering | "High engagement cluster" | Daily batch |
| **Predictive** | Propensity scoring | "Likely to refer" score > 70 | Daily batch |
| **Random** | Random assignment (traffic splitting) | 50% split for reward testing | On assignment |

## Variant Resolution Timing

**Critical Architectural Decision:** Variant resolution happens at **participant enrollment** (link generation time), NOT at referee click.

**"At Enrollment"** = the exact moment the client registers a user as a participant for a specific campaign. This is when `POST /v1/referrers/{id}/links` is called (or bulk enrollment, or CSV import). At that moment: platform evaluates participant attributes → matches to a variant → generates a referral link tied to that variant.

**"At Click"** (rejected) = would mean the participant gets a generic link at enrollment with no variant. Only when a referee clicks would the platform pick a variant — meaning the participant can't know what reward they're offering.

### Concrete Timeline Comparison

**Variant Resolution — When?**

  - At Enrollment ✓
    - *Feb 1* — Enroll Alice → Variant A (€50) → link
    - *Feb 1* — Widget: "Share and earn **€50**"
    - *Feb 5* — Bob clicks → Variant A
    - *Feb 8* — Carol clicks → Variant A
    - ✓ Alice always earns €50. Clear.
  - At Click ✗
    - *Feb 1* — Enroll Alice → generic link, no variant
    - *Feb 1* — Widget: "Share and earn... rewards" 🤷
    - *Feb 5* — Bob clicks → Variant A (€50)
    - *Feb 8* — Carol clicks → Variant B (€15)
    - ✗ €50 + €15 from same referrer. Confusing.

**The referrer experience demands Option A.** A participant who sees "Share and earn €50" must reliably earn €50 per qualified referral.

### Variant Allocation Fallback Chain

**Variant Allocation Fallback**

  → Enrolled with attributes
  → Evaluate segments in priority order
  - ┄ One match → assign  |  Multiple → random by weight  |  No match → default variant  |  No default → ineligible

For simple campaigns (one variant = the default): no evaluation needed — every participant gets the same variant.

### Re-Enrollment: When a Referee Becomes a Participant

A referee who converts and is later enrolled as a referrer (the growth flywheel, §4) is treated as a **brand-new participant enrollment**. They pass through variant resolution again, on **their own** participant attributes — they do **not** inherit the variant of the referrer who brought them in.

**No Variant Inheritance**

Alice (Variant A, €50) refers Bob → Bob converts → the client later enrolls Bob as a referrer. Bob is resolved against *his* attributes (e.g. SMB → Variant B, €25). Bob's reward is set by the variant *he* matched, not Alice's.

**Why no inheritance.** A referrer's variant encodes the deal *that referrer* was offered, sized to *their* segment. Passing it down would (1) let a low-value referrer mint high-value deals for everyone they refer, (2) break per-segment budgeting, and (3) make a participant's reward depend on who referred them rather than who they are — the opposite of the attribute-based, stable-€50 invariant. Inheritance is therefore forbidden; each enrollment resolves independently.

### What Data Drives Resolution (and Why Referee Click-Data Cannot)

Variant resolution reads **participant attributes the client supplies at enrollment** — `plan`, `mrr`, `country`, `account_age`, tags. These are authoritative facts from the client's own system.

The passive data we hold about a *referee* from their journey — email, IP-derived geo, device fingerprint — is **not** a participant-attribute set and is never used to resolve a variant. It is captured for attribution and fraud only. Two reasons it cannot drive resolution:

| Referee click-data | Why it can't resolve a variant |
| --- | --- |
| Email | Identifies a person, not a business tier; says nothing about plan / MRR / segment. |
| Geo (IP-derived) | Coarse and spoofable (VPN); a `country` rule needs the asserted billing country, not a guessed IP. |
| Device fingerprint | A fraud signal, not a segmentation attribute; using it to set rewards would be unreliable and a privacy problem. |

**Resolution rule when attributes are thin.** If the client enrolls someone but supplies *no* usable attributes (only what we passively know), no segment can match → the participant falls to the **default variant** (the catch-all in the fallback chain). They are still enrolled and can refer; they simply get the default deal until the client enriches their attributes.

### Missing Attributes Are the Normal Case (don't block)

Segments can target **any** participant attribute — plan, MRR, country, tenure, or something like `age`. But in the main acquisition flows the attribute often simply isn't known at enrollment, and that is **expected, not an error**:

- A referrer sharing on Facebook has no idea of their friend's age. The friend clicks, signs up on the client's site, and the client enrolls them as a participant on the spot — the referrer never supplied, and could not supply, that data.
- What signup captures (email, maybe name) rarely includes `age` or other segmentation fields.

**Rule: a missing attribute evaluates as "does not match" — never silently as a match — and the participant then follows the normal fallback chain to the default variant.** The system enrolls them with whatever attributes exist (possibly none) and gives the default deal. It must **not** block enrollment to wait for the attribute: blocking this flow loses the client brand-new users, the opposite of the product's job.

**Unknown age → default, still enrolled**

Campaign targets `age < 25 → Variant A (€30)` / `age ≥ 25 → Variant B (€20)`. User2 signs up via a Facebook link; the client knows no age. Neither age rule matches → User2 enrolls into the **default variant** and starts referring immediately. No one is blocked, nothing is guessed.

### Targeting vs Gating — the One Time Blocking Is Correct

Whether "unknown" should fall through or block depends on what the attribute is *for*:

| Attribute role | On missing → | Example |
| --- | --- | --- |
| **Targeting** (picks which deal) | `default` — fall through to default variant | age band only chooses €30 vs €20; unknown → default deal is harmless |
| **Compliance gate** (legal eligibility) | `block` — ineligible until supplied | age-restricted product (alcohol, gambling): enrolling an unknown-age person may be unlawful |

This is a per-segment flag, `on_missing_attribute: default | block`, whose **default value is `default` (non-blocking)**. `block` is the deliberate exception, chosen only for genuine legal gates with full awareness that it trades conversion for compliance safety. It is never the silent default.

### Progressive Attribute Enrichment

Because attributes like `age` usually arrive *after* enrollment, participant attributes are **enrichable over the participant's lifetime**, not frozen at enrollment:

**Enrich Later, Don't Block Now**

```
 signup (thin data) ─▶ enroll ─▶ default variant ─▶ can refer & earn now
        │
        │ later: client onboarding form / profile step / CRM sync supplies age
        ▼
   participant.attributes_updated(age=…)  ── recorded as an Event
        │
        ▼
   future segment evaluations can use it; existing enrollment NOT auto-changed
```

**Critical: enrichment does not silently re-resolve an existing enrollment.** Once enrolled at the default (or any) variant, learning the attribute later does **not** move the participant to a richer variant mid-flight — that would change a reward they may already be advertising, breaking the stable-reward invariant (Variant Resolution Timing, above). Late-arriving attributes affect **future** enrollments by default; upgrading an existing participant to a newly-matched variant is an explicit, operator- or rule-approved action (e.g. "promote at next campaign cycle"), never automatic.

### Why the Default Variant Carries More Weight Than It Looks

A direct consequence: in acquisition-heavy flows (Facebook shares, referee→participant conversion, any signup-time enrollment with thin data) the **default variant is frequently the most-used variant**, not a rare catch-all. Clients should size the default variant's reward and budget as a primary lever — its economics can dominate the program — rather than treating it as an afterthought fallback.

## Rule-Based Segment Syntax

**Important:** Segment rules evaluate attributes of the **participant** (the client's existing customer), NOT the referee. For example, `mrr >= 1000` means "only participants whose MRR is ≥€1000 can join this variant" — it controls who can be a referrer, not who can be referred.

```yaml
segment:
  name: "High-Value Enterprise DE"
  type: rule_based
  rules:
    AND:
      - field: plan            # participant's plan (passed at enrollment)
        operator: "in"
        value: ["enterprise", "enterprise_plus"]
      - field: country         # participant's country (passed at enrollment or IP-derived)
        operator: "="
        value: "DE"
  evaluation: real_time
```

## Eligibility Checkpoints

Each checkpoint evaluates specific rules before allowing the flow to continue. If any rule fails, the action is blocked.

### Entry Checkpoint (participant enrolls in campaign)

| Rule | What It Checks | Block Reason |
| --- | --- | --- |
| Campaign status | Is campaign active or scheduled? | "Campaign is not accepting participants" |
| Segment match | Does participant match any variant's segment? | "No matching variant for your profile" (unless default variant exists) |
| Dedup | Already enrolled in this campaign? | Skip (idempotent, return existing enrollment) |
| Participant status | Is participant banned or suspended? | "Account suspended" |
| Participant cap | Has campaign reached max participants? (if configured) | "Campaign is full" |

### Referral Checkpoint (referee clicks link, new referral created)

| Rule | What It Checks | Block Reason |
| --- | --- | --- |
| Campaign status | Is campaign still active? | "Campaign ended" |
| Participant status | Is participant still in good standing? | "Referrer account suspended" |
| Referral cap | Has participant reached max referrals per campaign? | "Referral limit reached" |
| Link expiry | Is the referral link still valid? | "Link expired" |
| Self-referral | Same email, IP hash, or device fingerprint as participant? | Silently blocked, flagged for fraud |

### Conversion Checkpoint (referee completes qualifying action)

| Rule | What It Checks | Block Reason |
| --- | --- | --- |
| Attribution window | Is referral within the attribution window? (e.g., 90 days from click) | "Attribution window expired" |
| Referee dedup | Has this referee already converted for this campaign? | "Already converted" |
| Fraud signals | Suspicious conversion timing, device, or geo patterns? | Flagged for review |

| Rule | What It Checks | Block Reason |
| --- | --- | --- |
| Budget | Has campaign budget been exhausted? | "Campaign budget depleted" |
| Reward cap | Has participant hit their reward cap? (per campaign or per period) | "Reward limit reached" |
| Fraud score | Is the overall referral pattern suspicious? (score > threshold) | Held for manual review |

### Payout Checkpoint (participant requests payout)

| Rule | What It Checks | Block Reason |
| --- | --- | --- |
| Payout method | Has participant set up a payout method? | "Please set up payout method" |

## Segmentation, Eligibility & the Primacy of Segments

Builds on the segmentation model above. Adds: how each segment type is *created*, real-time vs batch evaluation, and the conceptual argument for **why segmentation logically precedes experimentation** in this architecture.

### Segment Creation Modes

| Mode | How created | Evaluation | AI role | Human control |
| --- | --- | --- | --- | --- |
| **Manual / Static** | Operator picks members or uploads a list | On edit (membership frozen until changed) | none | full |
| **Rule-Based** | Operator writes attribute predicate (§5 syntax) | **Real-time** at enrollment | AI may *suggest* a rule | operator authors/edits rule |
| **AI-Generated** | Clustering over behavioral features proposes a group + label | **Daily batch** recompute | AI proposes; it is a Recommendation | operator must accept before use |
| **Predictive** | Propensity model scores; segment = score > threshold | **Daily batch** scoring | AI scores; threshold is human-set | operator sets threshold + reviews |
| **Random** | Deterministic hash split (§5) | On assignment, sticky | none | operator sets % + exclusion group |

**Real-time vs batch — the rule.** Anything evaluated at the *enrollment* decision (because variant resolution happens there, §5) must be real-time: static and rule-based qualify. AI-generated and predictive segments are batch-materialized into membership tables overnight, then read in real-time at enrollment — so the *read* is always fast even when the *compute* is heavy. This preserves the "stable €50 expectation" invariant: the segment a participant matched at enrollment does not silently shift mid-flight.

### How Segmentation, Eligibility, Events, Attribution & Fraud Interlock

**Gate Sequence**

```
 enrollment ─▶ [Segmentation resolves Variant] ─▶ [Eligibility: entry] ─▶ link issued
 referee click ─▶ Event(referral.created) ─▶ [Fraud: creation] ─▶ [Eligibility: referral]
 conversion ─▶ Event(conversion.recorded) ─▶ [Attribution resolves credit] ─▶ [Eligibility: conversion]
 reward calc ─▶ [Fraud: reward] + [Trust] ─▶ [Eligibility: reward] ─▶ approve|hold
 payout req ─▶ [Eligibility: payout] (method·hold·verify·tax) ─▶ payout.sent
```

> *Segmentation answers WHO and fixes WHAT (reward) up front; Eligibility answers WHETHER at each step; Fraud answers HOW RISKY; Attribution answers WHO GETS CREDIT. They never duplicate each other's job.*

### Why Segmentation Logically Precedes Experimentation

This is a design stance, not just a sequencing detail. Three reasons:

1. **An experiment is a comparison *within a defined population.*** A 50/50 reward test only means something if both arms draw from the same audience. The audience *is* a segment. Without segmentation first, an experiment compares apples (enterprise) to oranges (SMB) and the result is noise. Random segments (§5) are literally implemented as a segment type for exactly this reason.
2. **Variant resolution happens at enrollment (§5), so the experiment arm must be assignable at enrollment.** Assignment requires the participant already be classified — i.e. segmented — before the random split is applied within the eligible population. Mechanically, you cannot split a set you have not yet defined.
3. **Revenue-first analysis needs a stable denominator.** "Variant B lifted revenue per referrer 12%" requires that "referrer" means the same cohort across arms. Segmentation supplies that fixed denominator; experimentation measures movement against it.

Consequence for the product: the experiment framework (§6) is built *on top of* segments, never beside them. There is no separate "test audience" concept — a test is a mutually-exclusive random partition of an already-segmented population.

## Pulse Workflows

The Pulse table above lists the nine Pulse types and their triggers. Each Pulse is a **Temporal workflow template** instantiated per Referral. This section gives every Pulse its purpose, entry conditions, trigger event, reward-logic pattern, exit conditions, and failure/rollback handling, then a diagram. All Pulses share one skeleton; only the marked steps differ.

### Shared Pulse Skeleton (Temporal)

**Common Workflow Spine**

```
 START (referral.created)
   1. Fraud gate (creation)            ── compensate: cancel referral, no side effects
   2. Eligibility: referral            ── compensate: block, emit reason
   3. WAIT for trigger event ───────────  timer = attribution window
        ├─ trigger fires  ─▶ 4
        └─ timer expires  ─▶ EXIT(expired)
   4. Eligibility: conversion + Fraud gate (conversion)
   5. Attribution resolves credit
   6. reward.calculated (Pulse-specific formula)
   7. Trust + Fraud (reward gate) ─▶ approve | HOLD | reject
   8. Budget burn check (campaign auto-pause at 100%)
   9. reward.approved ─▶ hold timer ─▶ payout.sent
   COMPENSATION (saga): refund/chargeback → reward.reversed → ledger clawback → trust penalty
```

**Rollback model.** Each side-effecting step registers a compensating activity (Temporal saga). A late refund after `payout.sent` cannot un-send money, so its compensation is a *negative ledger entry* + trust penalty + (if pattern) fraud escalation — never a silent reversal. Workflows are durable: a crashed worker resumes from the last completed step; the `event_id` idempotency keys prevent double rewards on replay.

### Per-Pulse Specification

| Pulse | Purpose | Entry condition | Trigger event | Reward-logic pattern | Exit / timeout | Rollback specifics |
| --- | --- | --- | --- | --- | --- | --- |
| **Signup** | Lead/list growth | Active referrer, campaign live | `referee.signup` | Fixed, low (€/signup); often one-sided | Success on signup; expire at click-to-signup window (30d) | Fake-signup detected → reverse, reclaim, velocity flag |

## Enrollment Trigger (Per-Pulse)

When does a new person become an enrolled **participant** (variant resolved, outbound link live, able to invite)? This is the **enrollment trigger**, and it is a property of the **Pulse** — not the Playbook — because it depends on the pulse's value and fraud profile, which is intrinsic to the mechanic regardless of client or vertical. (Variant resolution and the freeze-at-enrollment invariant are unchanged; this only sets *when* that single resolution fires.)

**The safety rule.** Enrolling someone at *signup* and immediately showing the widget is safe only when both hold:

| Test | Question |
| --- | --- |
| **(a) Payout floor** | Is the eventual payout gated by a real *downstream conversion you control*, so early invites cost nothing until someone actually converts? |
| **(b) Cheap entry** | Is the entry condition self-evident or cheap-if-wrong — not a high-value, self-asserted, unverified claim? |

Pass both → `signup` is safe. Fail (a) → no floor, never widget-at-signup. Fail (b) → high-value unverified, require verification or a reward hold first.

### Trigger Values & Per-Pulse Defaults

| Pulse | Allowed triggers | Default | Why |
| --- | --- | --- | --- |
| **Conversion** | `signup`, `on_self_conversion`, `manual` | `signup` | Passes (a)+(b): downstream payment floor contains risk; entry is just a signup |
| **Reactivation** | `signup`, `on_self_conversion`, `manual` | `signup` | Same floor, but use **find-or-revive** (§7) — the person may already have a participant record |
| **Switch-Up** | `on_self_conversion` (verified), `manual` | `on_self_conversion` | Fails (b): high bounty on a self-asserted, unverified "I switched" claim — don't open a link until verified, or hold rewards |
| **Cross-Sell** | `on_self_conversion`, `manual` | `on_self_conversion` | Referrer is an existing customer; new participants arrive on their own product-B conversion |
| **Renewal** | `on_self_conversion`, `manual` | `manual` | About retaining existing customers; signup-time enrollment rarely applies |
| **Product Education** | `signup`, `on_self_conversion`, `manual` | `on_self_conversion` | Weak cash floor (milestone unlock, rarely cash); the milestone is the self-conversion analog |
| **Signup** | `manual` | `manual` | Fails (a): you pay per signup, so widget-at-signup lets unpaid signups farm signup rewards |
| **Newsletter** | `manual` | `manual` | Fails (a): no downstream payment floor |
| **Feedback** | `manual` | `manual` | Referee already converted; reward is for a review, not a new-participant flow |

### Who Sets It: Pulse → Playbook → Campaign

**Authority vs convenience**

```
 Pulse      declares ALLOWED triggers + DEFAULT   ← guardrail (can FORBID an unsafe one)
   │
 Playbook   may PRESET one of the allowed values  ← convenience preset, like reward amounts
   │
 Campaign/  may OVERRIDE within the allowed set    ← per-client tuning
 Variant
            (no layer can choose a trigger the Pulse does not allow)
```

**Payout is never an enrollment trigger.** Payout is the last step *after* a reward is earned and cleared — the end of the earning pipeline, not the start of the inviting pipeline. The only meaningful triggers are `signup`, `on_self_conversion`, and `manual`. Financial risk after early enrollment is managed by **reward holds** (§7–§8), not by delaying enrollment. The capability/payment timing this implies is detailed in §7 (Enrollment vs Self-Conversion).

## A/B Testing & Experimentation Framework

Grounded in the random-segment model and the primacy argument above (both in this section). Makes experimentation an explicit, first-class concept layered on segments.

### Model: Experiment = Random Partition of a Segment

**Segment → Experiment → Variants**

```
 Segment "Enterprise DE"          ← the fixed population (denominator)
      │ split (deterministic, sticky, mutually exclusive)
      ├─ Random 50% → Variant A (€25)   arm "control"
      └─ Random 50% → Variant B (€50)   arm "treatment"
                         │
                  measure on SAME population over time → pick winner
```

No standalone "test" entity is needed: an Experiment is metadata over a mutually-exclusive set of random segments feeding distinct Variants. This is why §5 insists segmentation precedes experimentation.

### What Can Be Tested

| Dimension | Held in | Example |
| --- | --- | --- |
| Reward amount / structure | Variant.reward_config | €25 vs €50; fixed vs tiered |
| Messaging / copy | Variant.messaging | "Earn €50" vs "Give 20%, get €50" |
| Surface / placement | Widget config | Inline vs floating widget |
| Timing | Pulse / enrollment rule | Enroll at signup vs at first payment |
| Channel mix | Share tools enabled | Email-only vs social share |
| Two-sided vs one-sided | Variant referee reward | Referee €25 credit on/off |

### Experiment Lifecycle & Success Criteria

**Experiment Lifecycle**

  Design  →  Run  →  Evaluate  →  Conclude  →  Roll-out  →  Discard

| Phase | Gate / metric |
| --- | --- |
| **Design** | Define population segment, arms, primary metric, MDE, `min_sample_size`, `min_test_duration_days` (reuse §11 statistical bounds) |
| **Run** | Sticky assignment; mutual exclusion enforced; no peeking changes |
| **Evaluate** | Primary: **revenue per referrer** / conversion rate / CAC payback (revenue-first, not signups). Require `confidence_threshold` (0.95). |
| **Conclude** | Winner if significant & sample/duration met; else inconclusive |
| **Roll-out / Discard** | Promote winning Variant to default for the segment, or discard and keep control |

### AI Interaction (advisory, bounded)

The AI may (i) *suggest* an experiment ("reward seems underpowered for SMB — test €25 vs €35"), and (ii) *interpret* results ("treatment lifted revenue/referrer 12%, p=0.03"). Both are **AI Recommendations** (§2): they never auto-launch or auto-conclude an experiment. Auto-application is allowed only through Incentive Optimization's bounded path (§11/§11) and only below `auto_approve_below`; anything that concludes an experiment or rolls out a winner is a Human Override. This respects the §11 guardrail that experiments and incentive changes honor statistical-rigor and pacing bounds.

## How Clients Register Participants (Referrer Enrollment)

Participants are the client's own users. The client decides who becomes a participant and when. Our platform provides tools for the client to register their users — we don't acquire participants ourselves.

**Key distinction:** - **Enrollment** = registering a user as a participant (getting them a link) — client pushes users into our platform - **Sharing** = an enrolled participant using their link to bring referees — widget, email, social, etc.

Widgets, email templates, and landing pages are **sharing tools** for already-enrolled participants, NOT enrollment mechanisms.

### Enrollment Methods

**Note — no auto-enrollment.** The platform does **not** run event-triggered auto-enrollment rules. Every participant is enrolled by an explicit client action (API single / bulk, CSV, or CRM connector). To enroll new customers on an ongoing basis, the client calls the enrollment API from their own backend at the relevant moment (e.g. on first payment) — the decision and the trigger live in the client's system, not ours.

## Enrollment vs Self-Conversion: Two Independent Clocks

A single person in a referral flow advances along **three independent clocks**. Most confusion about "when can they invite / when are they paid" comes from fusing them; they must stay separate.

**Three Clocks**

```
 1. ENROLLMENT TIME       person becomes a participant; variant resolved & frozen;
                          outbound link goes live   ──▶ governs "CAN INVITE"
 2. SELF-CONVERSION TIME  this person completes THEIR OWN qualifying action
                          (pays / reactivates / verified switch)  ──▶ gates NOTHING by default
 3. INVITEES' CONVERSIONS someone THEY referred converts
                          ──▶ governs "CAN BE PAID" (the normal earning rule)
```

| Capability | Gated by | NOT gated by |
| --- | --- | --- |
| Can invite others | clock 1 — enrollment time | their own conversion |
| Can be paid as referrer | clock 3 — invitees' conversions | their own conversion |
| Their own conversion (clock 2) | — gates nothing by default — | optional lever only (below) |

So a referee who has just signed up (clock 1 fired via a `signup`-triggered pulse, §6) can hold a live link and invite immediately. Their earnings read €0 not because *they* haven't paid, but because *no one they invited* has converted yet (clock 3). The two facts are unrelated.

### Self-Conversion Status Is Its Own Axis

Beyond operational state, trust level, and journey stage (§2), a participant carries an independent **self-conversion status**, backed by two timestamps:

| Field | Meaning |
| --- | --- |
| `enrolled_at` | When clock 1 fired — they can invite from here |
| `self_converted_at` (nullable) | When clock 2 fired — null for an enrolled-but-not-yet-converted referrer |

Storing both (not one) makes the "enrolled-but-never-self-converted referrer" population measurable — a cohort the `signup` trigger deliberately creates and that you will want to watch.

### Optional Lever: Gate Payout on Self-Conversion

For fraud-sensitive or high-value cases you *may* hold a referrer's earned rewards in the **Held** state (§8) until *their own* conversion (clock 2) clears — both a conversion nudge ("€40 waiting, subscribe to unlock") and a fraud dampener. This is **opt-in, not the default**: it can feel unfair to a genuine advocate who brought paying customers while still on a free plan, and it can suppress referral activity. Prefer trust limits and ordinary reward holds for routine risk; reserve this gate for specific high-value / low-verification pulses (e.g. Switch-Up).

### Reactivation: Revive, Don't Duplicate

When a `signup`-triggered Reactivation pulse (§6) brings back a churned user, that person may already have a participant record from their first life — possibly with prior referrals, holds, or a trust score. Reactivation enrollment must therefore **find-or-revive the existing participant** (rehydrating prior trust level and limits), never create a second record for the same person. Only genuinely new people create a new participant.

### Dual-Role Bookkeeping & Consent

At signup the person is simultaneously an **open referee** (their inbound referral still maturing toward the original referrer's reward) and an **active participant** (their outbound link is live). Two rules keep this clean:

- **Separate ledgers.** The inbound referral (credit owed to whoever referred them) and their outbound referrals (credit they may earn) are distinct; never net them against each other.
- **Self-referral guard covers the loop.** They must not be able to route their own outbound referral back into their own pending inbound one — the fraud check (Fraud Detection, below) treats that as a self-referral.

**Consent boundary.** Showing the widget *inside the client's app*, where the user already is, is part of the product experience — low risk. *Emailing* them to recruit is referral marketing and needs a lawful basis (§12); product signup is not consent to that. "See the widget" is fine; "get a recruitment email" is gated.

> **Invariant preserved.** Separating the clocks does *not* touch variant resolution, which stays pinned to enrollment time (clock 1) and frozen. If anything it protects the no-silent-re-resolution rule (§5): you are never tempted to "re-resolve when they finally convert", because clock 2 is decoupled from resolution.

## Trust Model

### What It Is (in one sentence)

The Trust Model is a **single per-participant score (0–100) that decides how much money we are willing to risk on that participant right now**, by setting four controls: monthly payout limit, hold period, reward-approval mode, and fraud-check depth. It starts tight (we have zero history) and loosens as clean behavior accumulates.

**Trust is not fraud detection.** Fraud detection asks "is *this event* suspicious?" (per-event, score 0–1, blocks/flags). Trust asks "how much do we trust *this person* overall?" (per-participant, score 0–100, sets privileges). Fraud outcomes feed Trust; Trust never blocks an individual event. Full comparison in the next subsection.

#### How a Score Becomes Privileges

**Trust Pipeline**

```
 INPUTS (history, per participant)        SCORE              LEVEL → PRIVILEGES
 ───────────────────────────────         ─────              ──────────────────
 account age 15% ┐                                          New        0–25  → €100/mo · 14d · manual
 success rate 25%├─ weighted ─▶ trust 0–100 ──map──▶        Established 26–50 → €500/mo · 7d  · auto <€50
 conv quality 20%│                                          Trusted    51–75 → €2k/mo  · 3d  · auto <€200
 fraud incid. 25%│ (negative)                               Advocate   76–100→ €10k/mo · instant · auto-all
 verification 15%┘
        ▲                                                          │
        └──────── recomputed on each relevant event ◀──────────────┘
                  (reward approved · fraud flag · verification · refund)
```

#### Is Trust Centralised?

**Yes for computation, no for scope.** One Trust service owns the scoring logic — a single source of truth, consistently versioned and auditable, so no campaign re-implements risk rules. But a score is scoped to **(participant × program)**, i.e. per client, and is **tenant-isolated**: a participant's trust at Client A never carries to Client B.

| Decision | Choice | Why |
| --- | --- | --- |
| Scoring logic | Centralised (one service) | Consistency, auditability, one place to tune / version |
| Score scope | Per participant, per program (tenant-isolated) | GDPR data separation; one client's fraud history isn't another's data; each client owns its own risk |
| Signal sharing within a program | All campaigns in a program feed one score | A fraudster abusing campaign X should lose trust in campaign Y of the same client |

**Trade-off locked in:** a genuinely trustworthy person starts cold at every new client. We accept that cost to keep tenants' personal data and risk decisions strictly separate.

**Applies to:** Participants only (not referees, not campaigns).

**Phase:** Lot 1. For MVP the score is bypassed by simple fixed rules: all rewards manual review, 7-day hold, €1,000/month limit for everyone.

### Trust Score Components

| Component | Weight | Description |
| --- | --- | --- |
| **Account Age** | 15% | Time since first referral |
| **Success Rate** | 25% | % of referrals that convert |
| **Conversion Quality** | 20% | LTV of referred customers |
| **Fraud Incidents** | 25% | Historical fraud flags (negative) |
| **Verification** | 15% | Email, phone, ID verified |

### Trust Levels

| Level | Score Range | Privileges |
| --- | --- | --- |
| **New** | 0-25 | €100/month payout limit, 14-day hold, manual review |
| **Established** | 26-50 | €500/month limit, 7-day hold, standard processing |
| **Trusted** | 51-75 | €2,000/month limit, 3-day hold, priority processing |
| **Advocate** | 76-100 | €10,000/month limit, instant payouts, auto-approval |

### Trust Level Effects — What Each Control Does

**Monthly payout limit** — how much money the participant can withdraw per month. NOT how much they earn — how much they can cash out. If Alice earns €3,000 this month but her limit is €500 (Established), she withdraws €500 now; the rest carries over to next month. This caps our exposure if Alice turns out to be running a fraud scheme.

**Payout hold period** — how long between "reward approved" and "money actually sent." During this window, the referee might request a refund, the conversion might be flagged as fraudulent, or abuse patterns might emerge. If we sent money instantly and the referral was fake, we'd never get it back.

**Reward approval mode** — does a human review this reward? For new participants, every reward goes through manual review. For Established, rewards under €50 auto-approve. For Advocates, everything auto-approves — their track record speaks for itself.

**Fraud check depth** — how thoroughly we examine each referral. Full checks for new participants (device fingerprint, IP analysis, timing patterns). Light checks for Advocates because false positives on trusted participants damage the relationship.

### Concrete Trust Progression Example

**Trust Progression**

  → **Month 1 — New** (5) — Manual review · €100/mo · 14d hold
  → **Month 6 — Established** (45) — Auto <€50 · €500/mo · 7d hold
  → ✓ **Year 2 — Advocate** (82) — All auto · €10k/mo · Instant

| Effect | New | Established | Trusted | Advocate |
| --- | --- | --- | --- | --- |
| Monthly payout limit | €100 | €500 | €2,000 | €10,000 |
| Payout hold period | 14 days | 7 days | 3 days | Instant |
| Reward approval | Manual | Auto < €50 | Auto < €200 | Auto all |
| Fraud check depth | Full | Standard | Light | Minimal |
| Support priority | Normal | Normal | Priority | VIP |

### Trust Model — Use-Case Flows

**Flow 1 — New participant, first reward (tight)**

  → Enroll → trust = New (score ~5)
  → Referral converts → reward.calculated €50
  → ⚠ New level → manual review required (regardless of amount)
  → ✓ Approved → 14-day hold → payout (capped at €100/mo)

**Flow 2 — Trust rising over clean months**

  → Months of conversions, no fraud, email + phone verified
  → Recompute: success 25% + quality 20% + age + verification ↑
  → ✓ Score crosses 50 → Trusted → auto-approve <€200, 3-day hold, €2k/mo

**Flow 3 — Fraud incident drops trust**

  → Chargeback + device-match cluster detected
  → ✗ Fraud-incidents component (25%, negative) spikes → score falls
  → ✗ Level drops (e.g. Trusted → Established) → tighter limits return
  → ⚠ Future rewards re-enter manual review until score recovers

**Flow 4 — Advocate, instant payout**

  → Score ≥ 76 → Advocate
  → ✓ Reward auto-approves (any amount within €10k/mo) → instant payout, minimal fraud check
  → ⚠ Safety valve: a high fraud score on a specific event still flags it, even for Advocates

| Confirmed fraud | Block + alert | Major score penalty |

## Fraud Detection

### Fraud Signals

| Signal | Severity | Description |
| --- | --- | --- |
| **Self-referral** | High | Same email, IP, or device fingerprint |
| **Velocity abuse** | Medium | Too many referrals too fast |
| **Disposable email** | Medium | Temporary email domains (mailinator, etc.) |
| **VPN/proxy** | Low | Masked IP address |
| **Device fingerprint match** | High | Same device, different accounts |
| **Payment reversal** | High | Chargebacks, refunds after reward |
| **Geographic mismatch** | Medium | IP location doesn't match profile |
| **Bot patterns** | High | Non-human interaction patterns |

### Fraud Checkpoints

| Checkpoint | Signals Evaluated | Auto-Block Threshold |
| --- | --- | --- |
| **Referral creation** | Self-referral, velocity, device | Score > 0.8 |
| **Qualification** | Conversion timing, device, geo | Score > 0.7 |
| **Reward approval** | Historical patterns, LTV | Score > 0.7 |
| **Payout** | Accumulated signals, account age | Score > 0.6 |

### Fraud Score Actions

| Score Range | Action |
| --- | --- |
| 0.0 - 0.3 | Auto-approve |
| 0.3 - 0.7 | Manual review required |
| 0.7 - 1.0 | Auto-block + alert |

### Fraud Flow — Signals → Score → Checkpoint → Action

**How a fraud decision is made**

```
 incoming event (click / conversion / reward / payout)
        │
        ▼  collect signals present on THIS event + participant history
   ┌────────────────────────────────────────────────┐
   │ self-referral(H) velocity(M) disposable(M)      │
   │ VPN(L) device-match(H) geo-mismatch(M) bot(H)   │   H/M/L = severity weight
   └────────────────────────────────────────────────┘
        │ weighted aggregate
        ▼
   fraud_score   0.0 ─────────── 0.3 ─────────── 0.7 ─────────── 1.0
                  │ <0.3            │ 0.3–0.7         │ > checkpoint threshold
                  ▼                 ▼                 ▼
            AUTO-APPROVE       MANUAL REVIEW     AUTO-BLOCK + alert
            (reward proceeds)  (reward HELD)     (reward blocked / reversed)
                  │                 │                 │
                  └────────┬────────┴────────┬────────┘
                           ▼                 ▼
                  outcome recorded     Trust model updates
                  as an Event (audit)  (incidents ↑ → score ↓)
```

> *Checkpoint threshold varies by stage: creation >0.8, qualification / reward >0.7, payout >0.6 — stricter the closer money is to leaving.*

**Worked example — self-referral attempt**

  → Referrer Alice's "referee" signs up from Alice's own device + same IP
  → ✗ Signals: device-fingerprint match (H) + geo overlap (M) → score 0.86
  → ✗ Creation checkpoint (>0.8) → referral auto-blocked, silently
  → ⚠ Alice's trust: fraud-incident component rises → score falls
  → Repeat pattern → Flagged → Suspended (participant state machine, §7)

## Tax Compliance & Reporting

### When Is Tax Relevant?

Referral rewards are taxable income for participants. Platform responsibilities vary by jurisdiction:

> **Short answer: the platform fills in and files a form with a tax authority only for US-resident participants.** For them it files `1099-MISC` once cumulative rewards reach $600/year. For participants in our launch markets (Germany, France, Spain) and the rest of the EU, the platform files **nothing** with any authority — it only gives the participant an annual earnings statement, and the participant self-declares. "Jurisdiction" here means the participant's own tax residency, not the client's.

| Jurisdiction | Threshold | Form Required | Withholding |
| --- | --- | --- | --- |
| **USA** | $600/year per participant | 1099-MISC | No (unless backup withholding) |
| **Germany** | €0 (all income taxable) | None from platform | No |
| **France** | €0 (all income taxable) | None from platform | No |
| **EU (general)** | Varies by country | None from platform | No |

### Platform Responsibilities

| Task | USA | EU (DACH, France) |
| --- | --- | --- |
| **Collect tax info** | W-9 before $600 threshold | Not required |
| **Report to authorities** | File 1099-MISC if ≥$600 | Not required |
| **Withhold taxes** | Only if W-9 not provided (24% backup) | Not required |
| **Inform participants** | Yes (annual summary) | Yes (annual summary) |

### Tax Calculation: When and How

**Tax Handling**

  → 1. Reward approved (€100)
  → 2. Tax check at payout — jurisdiction + W-9
  - ┄ EU: Pay €100, no withholding  |  US + W-9: Pay €100, report 1099  |  US no W-9: Withhold 24%
  → 4. Year-end: 1099 (US) / summary (EU)

### What Platform Does NOT Do

- ❌ Calculate participant's personal tax liability
- ❌ Provide tax advice
- ❌ Handle VAT (rewards are not services, no VAT applies)
- ❌ File taxes on behalf of participants

## Reward Mechanics & Campaign Compatibility

Builds on the reward model above. Specifies the reward **approval decision function** (auto-grant / hold / human review) and a **Reward × Pulse compatibility matrix**.

### Reward Approval Decision Function

Approval is the join of three inputs already in the spec — fraud score (§7), trust level (§7), and reward amount vs trust thresholds. Pseudocode, deterministic, auditable:

**approve(reward) →**

```
 if fraud_score > checkpoint_block_threshold      → BLOCK + fraud alert      (reversible)
 elif fraud_score in [0.3, 0.7]                   → HOLD for human review
 elif amount > trust.auto_approve_ceiling         → HOLD for human review
 elif budget_remaining < amount                   → BLOCK ("budget depleted")
 elif trust == Advocate                           → AUTO-APPROVE (instant)
 else                                             → AUTO-APPROVE then hold-period timer
 # MVP override: all rewards HOLD + manual review + 7d hold + €1000/mo (per §7 MVP rule)
```

| Outcome | When | Money moves | Reversible? |
| --- | --- | --- | --- |
| **Auto-grant** | Low fraud, amount under trust ceiling, budget OK | After hold period | Yes, during hold |
| **Held** | Mid fraud (0.3–0.7) OR amount over trust ceiling | Only after human approve | Yes |
| **Human approval required** | Same as Held; routed to Campaign Manager queue | On approve → enters hold | Yes |
| **Blocked/Reversed** | Fraud over checkpoint threshold, or refund/chargeback | None / clawback | n/a |

> **Revised Definition (Reward states).** §2 lists `Pending→Approved→Processing→Paid|Rejected|Reversed` but `Held` is used throughout §7–§8 without being a formal state. This v4 revision promotes **Held** to a first-class reward state between Pending and Approved: `Pending → Held → Approved → Processing → Paid | Rejected | Reversed`. Rationale in Appendix A.

### Reward × Pulse Compatibility Matrix

Rows = reward structure (§8); columns = Pulse (§6/§6). **R**ecommended · **A**llowed · **D**iscouraged · **F**orbidden, with one-line rationale below.

| Reward ↓ / Pulse → | Signup | Conversion | Reactivation | Cross-Sell | Renewal | Feedback | Newsletter | Switch-Up | Prod-Edu |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **Fixed** | R | A | R | A | D | R | R | R | R |
| **Percentage** | F | R | A | R | A | F | F | A | D |
| **Tiered** | A | R | A | A | D | D | A | A | A |
| **Recurring** | F | A | A | A | R | F | F | A | F |
| **Milestone** | R | A | A | A | D | A | R | A | R |
| **Capped** | A | R | A | R | R | A | A | R | A |

#### Key Rationales (risk · UX · complexity · compliance)

- **Percentage on Signup/Newsletter/Feedback = Forbidden:** no transaction value exists to take a percentage of — undefined and a fraud magnet.
- **Recurring on Signup/Newsletter/Feedback/Prod-Edu = Forbidden:** no recurring revenue to share; would pay forever for a one-off act.
- **Fixed on Renewal = Discouraged:** retention reward should scale with retained value; a flat fee under- or over-pays. Capped/Recurring fit better.
- **Capped is broadly Recommended/Allowed:** bounds exposure (fraud-by-design) regardless of Pulse — a safe default.
- **Tiered on Feedback = Discouraged:** incentivizing review *volume* per person risks fake/low-quality reviews and platform-policy issues (G2/Capterra).
- **Percentage on Prod-Edu = Discouraged:** milestone is an activity, not a sale; credit/unlock rewards align incentives better than cash %.

## Attribution Matching: How Events Link Together

### The Core Problem

```
Day 1:  Participant Alice shares link (ref_code: ALICE42)
Day 3:  Anonymous visitor clicks link
Day 5:  Visitor signs up as "bob@example.com"
Day 30: Bob makes first payment

Question: How does RefRev know Bob came from Alice?
```

RefRev supports **two attribution methods**. Choose based on your stack:

| Method | Best For | Requires |
| --- | --- | --- |
| **Method A: referee_id** | Any backend | Client sends events to RefRev API |
| **Method B: Payment Provider** | Stripe/Paddle/Chargebee users | Webhook integration |

---

### Method A: referee_id Matching (Recommended)

Client backend sends events with `referee_id` (your internal user ID) as the primary key.

**Pros:** - Works with any backend/payment system - `referee_id` survives email changes - Full control over when events are sent

**Cons:** - Requires client to send events to RefRev API

---

### Method B: Payment Provider Metadata (Stripe/Paddle/Chargebee)

RefRev reads attribution from payment provider metadata via webhooks. No need to send conversion events.

**Method B: Payment Provider Metadata**

  → **1. Click** — Same as A — cookie stores ref_code
  → **2. Signup** — Client attaches to Stripe Customer: `metadata: { refrev_ref_code }`
  → ✓ **3. Webhook** — Stripe sends payment event → RefRev reads metadata → credits Alice

> *Works with Stripe, Paddle, Chargebee. Future payments auto-attributed.*

**Supported Payment Providers:**

| Provider | Webhook Events | Metadata Field |
| --- | --- | --- |
| **Stripe** | `invoice.payment_succeeded`, `checkout.session.completed` | `customer.metadata` |
| **Paddle** | `subscription.created`, `transaction.completed` | `custom_data` |
| **Chargebee** | `payment_succeeded`, `subscription_created` | `meta_data` |

**Pros:** - 100% server-side attribution (immune to ad blockers) - No need to send conversion events - Future payments auto-attributed

**Cons:** - Requires Stripe/Paddle/Chargebee - Must attach metadata at customer creation

#### Does Method B also tell us which referee it is?

Yes. The payment webhook always carries the provider's **customer id** (and usually email) plus the `ref_code` we asked the client to place in metadata. So Method B identifies the referee by the *payment-provider customer id*, whereas Method A identifies them by the *client's internal `referee_id`*. Different key, same purpose.

#### So do Methods A and B change anything in our implementation?

**They differ only at the ingestion edge, then converge.** The platform has one attribution *resolver*; what changes is which *ingestion adapter* feeds it and which matching key the event carries:

**Two adapters, one resolver**

```
 Method A:  client backend ─ POST /v1/events {referee_id, ref_code} ─┐
                                                                    ├─▶ Attribution Resolver ─▶ Referral + Reward
 Method B:  payment webhook ─ {provider_customer_id, ref_code} ─────┘     (priority key ladder, below)
```

So it is neither "no difference" nor "two separate systems": Method A needs the client to send events and keys on `referee_id`; Method B needs no client event code and keys on the provider customer id. Both land as normalized events the resolver treats identically.

---

### Choosing a Method

| Scenario | Recommended Method |
| --- | --- |
| Using Stripe/Paddle/Chargebee | **Method B** (simpler, more reliable) |
| Using other payment provider | **Method A** (referee_id) |
| Want both signup AND conversion tracking | **Both** (Method A for signup, Method B for conversion) |
| No payment provider (lead gen only) | **Method A** (referee_id) |

### Matching Keys Summary

| Key | Source | Reliability |
| --- | --- | --- |
| `referee_id` | Your internal user ID | ✅ Best — deterministic |
| Payment provider customer ID | Stripe/Paddle/Chargebee | ✅ Best — immutable |
| `referee_email` | User's email | ⚠️ Good — can change |
| `click_id` | Generated on click | ⚠️ Fallback — links click to signup |

#### What the Ingestion Service Does With These Keys

Every inbound signal (SDK event, `POST /v1/events`, payment webhook) hits one **ingestion service** that does two jobs: (1) **normalize** the payload into a canonical event, and (2) hand it to the **resolver**, which walks the keys in **priority order** and stops at the first that matches an open referral for the referee.

**Resolution Key Ladder (per event)**

```
 normalized event
   │ try in order, stop at first hit
   ├─ 1. ref_code in payload ............ direct → done (most events have this)
   ├─ 2. provider_customer_id ........... Method B match → done
   ├─ 3. referee_id (client internal) ... Method A match → done
   ├─ 4. referee_email .................. match (may have changed) → done
   ├─ 5. click_id ....................... correlate click → signup → done
   └─ none .............................. record as ORGANIC (no credit)
```

| Key | When it is the one actually used |
| --- | --- |
| `ref_code` | The referee arrived with an explicit code (cookie / URL / metadata) — the normal case. |
| provider customer id | Method B: conversion came from a payment webhook with no `referee_id`. |
| `referee_id` | Method A: client sent the event keyed by its own user id. |
| `referee_email` | Last resort when no id / code is present (e.g. email-only invitation flow). |
| `click_id` | Stitches an anonymous click to a later signup when nothing else links them. |

#### Can matching keys be mixed in the same campaign?

**Yes — mixing is expected, and it is resolved per event, not per campaign.** Resolution is decided one event at a time by the ladder above, so within one campaign one referee may resolve by `ref_code`, another by provider customer id (Method B), another by `referee_id` (Method A). A campaign can even run Method A for signups and Method B for payments at the same time (see "Choosing a Method"). The only rule is the priority order, which guarantees the most reliable available key wins and the same conversion is never double-credited (idempotency on `event_id`).

## Touch, Revenue-First Attribution & Analytics

Deepens the attribution model above. Adds touch storage/retention, the shared event basis all attribution models run on, complex multi-participant timelines, and — the core differentiator the base model omits — **how MRR/ARR is attributed back to referrals**.

### Touch Storage & Retention

| Layer | Store | Granularity | Retention | Purpose |
| --- | --- | --- | --- | --- |
| Raw touches/events | ClickHouse (append-only) | Per-interaction, full context | 13 months hot, then aggregate-only | Attribution replay, fraud forensics |
| Attribution results | RDS (Analytics) | Per-conversion credit split | Life of program + legal min | Reward justification, audit |
| Revenue rollups | ClickHouse materialized views | Daily × campaign × variant × segment | Indefinite (aggregate, non-PII) | MRR/ARR dashboards, Health score |
| PII linkage (referee email/IP-hash) | RDS, pseudonymized | Per-referee | Minimized; erased on DSR (§12) | Dedup, self-referral detection |

**One log, many models.** First/Last/Linear/Time-Decay/Position/AI-weighted (§10) are *not* different pipelines — they are different reducer functions over the same ordered Touch list per referee. Switching a campaign's model recomputes credit from stored touches; no re-instrumentation. This is why touches are stored at full granularity even though MVP only uses first-touch.

### Complex Journey — Multiple Participants & Channels

**Multi-Touch Timeline (same referee)**

```
 Day 1  Alice shares (LinkedIn)        ── touch t1 (click)   participant A
 Day 4  Bob shares (email)            ── touch t2 (click)   participant B
 Day 6  referee signs up                conversion C0 (signup, €0)
 Day 30 referee first payment €100/mo    conversion C1 (MRR €100)
 Day 90 referee upgrades to €150/mo      expansion E1 (ΔMRR +€50)
 Day 365 referee renews                  renewal R1 (ARR €1800 retained)

 first-touch  : 100% → A          (MVP default; reward integrity preserved)
 last-touch   : 100% → B
 linear (V2)  : 50% A / 50% B     ← analytics view ONLY (see invariant below)
 revenue link : C1,E1,R1 all trace to the SAME referral_id → A's revenue ledger
```

> **Revised Definition / contradiction resolved (multi-touch vs reward integrity).** §10's Linear model splits a reward across A and B. But §5's invariant — a referrer who sees "earn €50" must reliably earn €50 — breaks if B's arrival silently halves A's payout. Resolution: **separate analytics attribution from reward attribution.** Multi-touch models (Linear/Time-Decay/Position/AI) drive *reporting and credit insight*; the *payout* defaults to single-winner (first- or last-touch, per campaign) so the promised amount holds. Splitting actual rewards is an explicit, opt-in campaign setting that must change the referrer-facing copy to "share of up to €50". See Appendix A.

### Revenue-First Attribution (MRR / ARR)

The differentiator: credit is measured in recurring revenue, not signup counts. Mechanism:

1. **Conversion carries value.** `conversion.recorded` includes `mrr_value` (and plan/term), sourced from the payment-provider webhook (Method B) or client event (Method A). Signup-only pulses record €0 and are counted separately.
2. **Referral is the durable key.** Every later revenue event from that referee — expansion, cross-sell, renewal — references the original `referral_id`, so expansions accrue to the participant who first referred them.
3. **Rollups compute attributed MRR/ARR.** ClickHouse materialized views sum `mrr_value` by participant / variant / segment / cohort month.

**From Touch to ARR**

```
 Touch ─▶ Conversion(mrr=€100) ─▶ AttributionResult(participant=A, referral=r1)
                                      │
   expansion(+€50)  ─references r1──▶ │  Σ → Attributed MRR(A) = €150
   renewal(retain)  ─references r1──▶ │  Σ → Attributed ARR(A) = €150 × 12 = €1,800
                                      ▼
                          Revenue-first dashboard: MRR/ARR per referrer,
                          CAC payback, expansion %, cohort retention
```

| Revenue-first metric | Definition | Why it beats signup-counting |
| --- | --- | --- |
| Attributed MRR | Σ recurring value of conversions credited to a participant | Distinguishes a referrer of €5/mo hobbyists from one of €500/mo enterprises |
| Attributed ARR | Attributed MRR × 12 (or contract term) | Board-level number; ties referrals to revenue plan |
| Expansion attribution | ΔMRR from upgrades/cross-sell on referred accounts | Credits long-tail value the original referral seeded |
| CAC payback (per referrer) | Reward paid ÷ attributed MRR | Tells you which referrers are profitable, not just active |
| Revenue per referrer | Attributed ARR ÷ active referrers | The denominator experiments (§6) move |

## Incentive Optimization

**Phase: Lot 2.** Requires significant conversion data to work. Not feasible in MVP or early campaigns.

### What It Is

AI analyzes conversion data and recommends reward adjustments to maximize ROI. Think of it like giving a junior employee a company credit card with spending limits — they can make purchases, but within strict constraints.

### Example

**Incentive Optimization Example**

- **SMB** — €25 → 5% conv
- **Enterprise** — €25 → 12% conv

- **SMB → €31** max_increase 25% caps it
- **Enterprise → €22** already converting well

### Optimization Bounds — What They Are and Why

Bounds are guardrails that prevent the AI from making reckless changes. The client configures these in the campaign settings.

**Reward range bounds** — absolute floor and ceiling:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `min_reward_amount` | Floor — never go below this | €10 | "€5 is insulting, don't suggest it even if data says so" |
| `max_reward_amount` | Ceiling — never go above this | €200 | "We can't afford more than €200 per referral regardless" |

**Change rate bounds** — how much can change in one step:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `max_increase_percent` | Cap upward jumps | 25% | "Current is €25 → max AI can suggest is €31.25. Prevents sudden spikes that attract fraud." |
| `max_decrease_percent` | Cap downward drops | 15% | "Current is €100 → min AI can suggest is €85. Prevents angering active participants with sudden cuts." |

**Budget protection bounds** — don't blow the budget:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `max_daily_budget_impact` | Extra cost per day | €500 | "If raising SMB from €25→€31 at 30 conv/day = €180/day extra. Under €500, so OK. At 100 conv/day = €600/day → BLOCKED." |
| `max_monthly_budget_impact` | Extra cost per month | €5,000 | "Catches multiple small changes that individually pass daily check but accumulate." |
| `max_total_budget` | Campaign hard cap | €50,000 | "When cumulative rewards approach this, AI stops suggesting increases." |

**Statistical rigor bounds** — don't act on noise:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `min_sample_size` | Need enough data | 100 conversions | "With 15 conversions, a 20% rate could be 3/15 — meaningless noise. Wait for 100+." |
| `confidence_threshold` | Statistical confidence | 0.95 (95%) | "AI must be 95% sure the change will help before suggesting it." |
| `min_test_duration_days` | Capture full cycles | 7 days | "Monday conversions differ from Saturday. 7 days captures the full weekly cycle." |

**Pacing bounds** — don't change too fast:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `cooldown_days` | Gap between changes | 7 days | "After one change, wait 7 days to measure impact. Changing Monday then Wednesday makes data unreadable." |
| `max_changes_per_week` | Total change frequency | 2 per week | "Even across different variants, max 2 changes per week." |

**Human oversight bounds** — big decisions need approval:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `auto_approve_below` | Small changes go fast | €20 | "Change of €15 (€25→€40) auto-applies. No human review needed." |
| `require_approval_above` | Big changes need human | €50 | "Change of €55 (€25→€80) sends notification to Campaign Manager. Must approve in dashboard." |

**Exclusion bounds** — protect special segments:

| Bound | Purpose | Example | Plain English |
| --- | --- | --- | --- |
| `excluded_segments` | AI can't touch these | ["vip"] | "VIP rewards are managed manually. Too important for automated changes." |
| `excluded_reward_types` | AI can't change these types | ["cash"] | "Cash rewards are fixed. AI can only adjust credit/discount rewards." |

### Scenario Examples

**Scenario 1: AI wants to increase SMB reward from €25 to €40**

**Scenario: Increase blocked**

max_increase = 25% · €25 × 1.25 = €31.25 max · €40 > €31.25 → **BLOCKED** → adjusted to €31

**Scenario 2: AI wants to decrease Enterprise reward from €100 to €70**

**Scenario: Decrease blocked**

max_decrease = 15% · €100 × 0.85 = €85 min · €70 < €85 → **BLOCKED** → adjusted to €85

**Scenario 3: AI recommends €45 change (from €30 to €75)**

**Scenario 4: AI recommends €60 change (from €40 to €100)**

### Example Configuration

```yaml
incentive_optimization:
  enabled: true
  bounds:
    # Reward limits
    min_reward_amount: 10          # Never below €10
    max_reward_amount: 200         # Never above €200

    # Change limits
    max_increase_percent: 25       # Max 25% increase per change
    max_decrease_percent: 15       # Max 15% decrease per change

    # Budget limits
    max_daily_budget_impact: 500   # Max €500/day extra
    max_monthly_budget_impact: 5000 # Max €5,000/month extra

    # Statistical requirements
    min_sample_size: 100           # Need 100 conversions first
    confidence_threshold: 0.95     # 95% confidence required

    # Timing
    min_test_duration_days: 7      # Wait 7 days minimum
    cooldown_days: 7               # 7 days between changes
    max_changes_per_week: 2        # Max 2 changes/week

    # Approval thresholds
    auto_approve_below: 20         # Auto-apply if < €20 change
    require_approval_above: 50     # Need approval if > €50 change

    # Exclusions
    excluded_segments: 
      - "vip"
      - "enterprise_custom"
    excluded_reward_types: []
```

## AI System Model & Program Health Score

Consolidates the AI features above into a per-feature system contract and makes **Program Health Score** first-class (it was referenced but undefined). Every feature is described by input → output → decision surface → human control → risk.

### AI Feature Contracts

| Feature | Inputs (domains/events) | Output & scope | Decision surface | Human-in-loop | Risk |
| --- | --- | --- | --- | --- | --- |
| **Program Setup Assistant** | Public website scrape, Playbooks | Draft Campaign + Variants + reward range | Recommendation only | Operator approves before publish | Low |
| **Playbook / Segmentation recs** | Analytics rollups, propensity | Suggested segments + rules + labels | Recommendation only | Accept to materialize | Low |
| **Incentive Optimization** | Conversion/revenue analytics | Reward delta proposal | Decision *within bounds* (§11); else Recommendation | Auto below `auto_approve_below`; approval above | Medium |
| **Propensity Scoring** | Behavioral, engagement, account features | 0–100 scores + factors | Scoring only (no mutation) | n/a (informs targeting) | Low |
| **Fraud Detection & Trust Scoring** | Event log, device/IP, velocity | Fraud score per event; trust score per participant | Auto-block at score > checkpoint threshold; else flag | Review queue 0.3–0.7; override/reinstate | High |
| **Program Health Score** | Funnel, revenue, fraud, saturation rollups | 0–100 composite + sub-scores + alerts | Calculation only | n/a (drives insights) | Low |
| **AI Insights Panel** | Health sub-scores, anomalies, experiments | Prioritized natural-language insights + suggested actions | Recommendation only | Operator acts/dismisses | Low |

**Recommendation vs Decision discipline.** Only two features ever mutate state autonomously, both narrowly: Incentive Optimization (sub-threshold reward tweaks) and Fraud (high-score auto-block). Everything else is advisory. Each Decision logs its triggering Recommendation, the bounds it satisfied, and is reversible by Human Override (§2) — enforcing Explainable + Overridable structurally.

### Program Health Score (first-class)

One tracked 0–100 number per Program, recomputed nightly, decomposed into four weighted sub-scores. It is the signal the Insights Panel and proactive alerts run on.

| Sub-score | Weight | Measures | Degrades when… |
| --- | --- | --- | --- |
| **Referral Funnel** | 30% | Share→click→signup→conversion rates vs baseline | Drop-off at any funnel stage rises |
| **Revenue Impact** | 35% | Attributed MRR/ARR trend, CAC payback, expansion | Revenue per referrer falls or payback worsens |
| **Fraud Pressure** | 20% | Share of flagged/blocked/reversed rewards | Fraud rate climbs, reversals spike |
| **Audience Saturation** | 15% | % of eligible base enrolled & still converting | Pool exhausted; new enrollments stop converting |

**Health Score → Insights → Action**

```
 nightly: health.recomputed
   ├─ Funnel 30 · Revenue 35 · Fraud 20 · Saturation 15  →  composite e.g. 72/100
   ▼
 AI Insights Panel (proactive)
   "Revenue sub-score ↓8 this week: SMB variant conversion fell after reward cut.
    Suggested: revert SMB reward to €25 (Recommendation)."        → operator Override
   "Fraud pressure ↑: device-match cluster on campaign Q1.
    3 participants flagged for review."                            → review queue
```

**Why a single composite.** Clients running multi-variant, multi-campaign programs cannot watch every metric. Health collapses the state into one number with drill-down, and lets the AI surface *what changed and why* — the proactive, embedded-AI posture rather than a chatbot to interrogate.

# 12. Compliance & Privacy (EU-First)

§9 covers consent and cookies; §8 covers tax. This section maps the whole platform to GDPR/ePrivacy: lawful basis, minimization, purpose limitation, DSRs, retention, and audit of automated decisions.

## Lawful Basis & Purpose Map

| Processing | Lawful basis (GDPR Art. 6) | Purpose limit | Notes |
| --- | --- | --- | --- |
| Participant enrollment & reward | Contract / legitimate interest (client is controller) | Run the referral program only | Platform is processor; client is controller |
| Referee click/conversion tracking | Consent (functional cookies, ePrivacy) | Attribution only | Denied → server-side URL attribution only (§9) |
| Fraud signals (IP-hash, device fp) | Legitimate interest (fraud prevention) | Fraud detection only | Documented LIA; minimized; short retention |
| Propensity / AI scoring | Legitimate interest | Targeting & optimization | Pseudonymized features; no special-category data |
| Payout (email, provider ref) | Contract | Pay the reward | Sensitive bank data held by payout Partner, not platform (§8) |

## DSR Propagation Across Services

A data-subject request (access / erasure / portability) is an Event that fans out; each domain owns its own deletion/anonymization:

**Erasure Fan-out**

```
 dsr.requested(subject) ─▶ Compliance orchestrates (Temporal)
   ├─ Identity:    remove/anonymize user record
   ├─ Tracking:    anonymize touches (keep aggregate counts, drop PII keys)
   ├─ Rewards:     retain financial records (legal basis) but pseudonymize identity
   ├─ Analytics:   purge PII linkage; aggregates survive (non-identifying)
   ├─ AI:          drop subject from feature store + retrain trigger
   └─ Integrations: signal connected Partners to delete (where applicable)
 ─▶ erasure.completed (audit.logged with per-service receipts)
```

**Tension handled honestly:** erasure vs. financial/tax retention. Resolution: monetary ledger entries are retained under legal-obligation basis but stripped of identifying fields beyond what tax law requires; the subject is told this in the DSR response.

## Retention & Decision Audit

| Data class | Retention | Then |
| --- | --- | --- |
| Raw touches/events (PII-bearing) | 13 months | Anonymize → aggregate-only |
| Fraud signals | Minimal (e.g. 90d post-resolution) | Delete; keep outcome flag |
| Reward/payout ledger | Legal min (tax: years) | Pseudonymize identity |
| Consent records | Proof-of-consent lifetime + buffer | Archive |
| AI/fraud decision audit log | Program life | Immutable, queryable |

**Automated-decision auditability (GDPR Art. 22-adjacent).** Every AI Decision and fraud auto-block writes an audit record: model version, input window, score, bound satisfied, and any Human Override. Participants affected by an automated block can be given a human review path — the review queue already exists for 0.3–0.7 scores. Data residency: all primary stores in EU regions; Partners selected for EU processing where offered (§4).
